# ESCOPO DE IMPLEMENTAÇÃO

## 1. Autenticação e proteção de rotas

Implementar sobre `AuthProvider.tsx` e rotas atuais:
- login;
- logout;
- estado de carregamento;
- estado não autenticado;
- protected routes;
- tratamento de usuário sem membership ativa;
- redirecionamentos coerentes;
- nenhuma rota privada protegida apenas por UI.

Não implementar portal do paciente neste GOAL.

## 2. Tenant Resolver + Tenant Context

Criar resolução centralizada e confiável:

`tenantSlug -> tenantSlugs/{slug} -> tenantId -> tenant ativo -> configuração`

Requisitos:
- slug inválido => 404/estado de tenant não encontrado;
- tenant `suspended` ou `archived` não opera normalmente;
- `tenantId` nunca é aceito livremente do cliente como autorização;
- áreas privadas deixam de usar `demoData` como source of truth;
- branding/public profile vem do tenant quando aplicável;
- demo data pode permanecer apenas em modo explicitamente demonstrativo/dev.

## 3. Memberships + RBAC

Usar o modelo já existente:

`tenants/{tenantId}/memberships/{uid}`

Preservar os papéis:
- `tenant_owner`
- `tenant_admin`
- `dentist`
- `receptionist`
- `assistant`

Implementar:
- carregamento de membership ativa;
- role e permissions;
- guards de rota/ação;
- membership inativa => acesso negado;
- usuário de Tenant A não pode operar Tenant B;
- menor privilégio;
- `receptionist` sem `clinical.write`;
- `assistant` restrito conforme permissions atuais.

Não inventar papéis só para padronizar o ecossistema.

## 4. Platform Owner

Tornar o conceito já modelado operacional:
- reconhecer `platform_owner` de modo seguro;
- proteger `/platform`;
- listar tenants reais;
- criar tenant mínimo;
- criar/associar slug;
- criar owner/membership inicial;
- ativar/suspender tenant sem apagar dados;
- configurar branding básico;
- auditar ações administrativas sensíveis.

Platform Owner NÃO deve ter acesso clínico casual.

Preservar o modelo de suporte clínico temporário já presente em Rules (`platformSupportAccess/{tenantId}`), exigindo:
- ator;
- tenant;
- motivo;
- expiração;
- audit log.

## 5. Firestore Rules e isolamento

Endurecer `firestore.rules` apenas onde necessário e provar comportamento com Firebase Emulator + `@firebase/rules-unit-testing` ou equivalente.

Garantir:
- Tenant A não lê/escreve Tenant B;
- membership precisa estar `active`;
- permissions são verificadas;
- dados no documento não podem contradizer tenant do path;
- acesso clínico do Platform Owner exige suporte temporário válido;
- pacientes não são deletados silenciosamente;
- registros clínicos consolidados são append-only;
- amendments são novos registros;
- audit logs não podem ser forjados arbitrariamente;
- chamadas diretas ao Firestore não burlam autorização.

O teste atual `tests/tenantIsolation.test.ts` não é prova suficiente por si só. Substituir/complementar com testes reais de Rules.

## 6. Persistência do núcleo operacional

Substituir demo data como fonte operacional e persistir:
- professionals;
- patients;
- procedures;
- scheduleResources;
- appointments.

Implementar CRUD mínimo respeitando permissões.

Regras:
- queries privadas sempre tenant-scoped;
- IDs/paths derivados do TenantContext;
- sem hardcode de tenant demo;
- evitar exclusão destrutiva quando histórico/referência exigir inativação/soft state;
- tratar loading/empty/error.

## 7. Agenda + anti-double-booking confiável

Preservar `src/modules/scheduling/availability.ts` como lógica de domínio, mas não usá-la como única proteção.

Criação/remarcação de appointment deve validar em camada confiável:
- tenant ativo;
- professional ativo;
- start/end válidos;
- conflito do mesmo professional;
- conflito do mesmo `resourceId` quando houver;
- bloqueios/indisponibilidades já modelados;
- appointment cancelado não bloqueia;
- concorrência/race condition não cria double booking.

Não aceitar solução em que somente frontend verifica conflito.

Use camada confiável compatível com a stack já aprovada. Preferir Cloudflare Worker quando adequado, sem introduzir serviço pago não aprovado.

Se houver impedimento técnico real que exija mudança relevante de infraestrutura/custo, pare essa parte e documente a decisão necessária. Não reduza o requisito de integridade.

## 8. Prontuário clínico P0

Implementar o modelo já aprovado:
- `ClinicalRecord`;
- `ClinicalRecordAmendment`.

Regras:
- registro original append-only;
- sem update/delete direto do registro consolidado;
- correção por amendment;
- tenantId;
- patientId;
- professional responsável;
- actor/author;
- timestamp;
- appointmentId opcional;
- `clinical.read` / `clinical.write`;
- auditabilidade de mutações relevantes.

Odontograma e plano de tratamento ficam fora deste GOAL.

## 9. Mídia clínica privada em R2

Endurecer `workers/media-api/src/index.ts`.

O comportamento atual de considerar apenas `res.ok` ao ler membership NÃO é suficiente.

Para upload exigir:
- token Firebase válido;
- tenant ativo;
- membership ativa ou suporte clínico temporário válido;
- permission `clinical.write` para membro do tenant;
- patientId pertencente ao mesmo tenant;
- content type permitido;
- tamanho máximo técnico razoável;
- object key tenant-scoped;
- metadata com `tenantId`, `patientId`, `uploaderId`;
- registro de metadata no Firestore quando necessário para o fluxo clínico;
- nenhuma URL pública permanente.

`storage.rules` permanece deny-all enquanto Firebase Storage não for a arquitetura ativa de fotos clínicas.

Não implementar ainda limite comercial de 10/50/200 GB.

## 10. Audit logs essenciais

Implementar auditabilidade para ações deste GOAL:
- criação/suspensão de tenant;
- alteração de membership/role;
- ativação/revogação de suporte clínico;
- alteração clínica relevante;
- mudança de configuração sensível;
- ações administrativas críticas.

Campos mínimos:
- actorId;
- actorRole;
- tenantId;
- action;
- resourceType;
- resourceId;
- timestamp;
- before/after somente quando seguro e necessário.

Nunca registrar secrets ou conteúdo clínico desnecessário em logs.

## 11. Dois tenants fictícios de teste

Não existe cliente real original comprovado.

Criar fixtures de testes/emulator:
- Tenant A;
- Tenant B.

Provar isolamento de:
- patients;
- professionals;
- appointments;
- clinical records;
- clinical media;
- branding;
- memberships.

Dentist A não pode acessar Patient B.

Usar somente dados fictícios.
